# 使用者需求整理

日期：2026-06-30

這份文件記錄接手後收到的使用者需求。先把需求講清楚，再決定要不要做、怎麼做。不要直接把聊天截圖變成程式碼，否則很容易做出一個看起來有功能、實際上責任不清的模組。

## 需求 001：行事曆 / 回診提醒 / 看護請假

來源：內部 LINE 對話截圖，2026-06-30 提供。

截圖內容是 LINE 對話。使用者提出：

> 新增行事曆功能，讓外籍看護預知後續回診日程安排。外籍看護也會請假。

這句話可以拆成兩個需求：

1. 家屬或照護管理者可以建立後續行程，例如回診、復健、拿藥、檢查、家訪。
2. 外籍看護可以知道接下來的安排，也可以提出或記錄請假。

### 目前系統缺口

目前 CareTaiwan 有照護紀錄、醫護卡、家屬 LINE 推播、記帳與核帳。它還沒有「未來行程」的資料模型，也沒有請假流程。

所以這不是單純新增一個頁籤。它會影響：

- 資料庫 schema。
- 看護端首頁與底部導覽。
- 家屬端建立與修改行程的權限。
- LINE Bot 提醒與通知。
- 多語文案。
- 隱私權政策與資料保留說明。

### 建議的第一版範圍

先做小，不要一開始就接 Google Calendar 或醫院系統。

第一版只處理「照護行程」：

- 家屬端可以新增、修改、刪除行程。
- 看護端可以查看未來 7 天 / 30 天行程。
- 行程可以綁定某一位長者。
- 行程類型先用固定選項：回診、復健、拿藥、檢查、家訪、其他。
- 行程欄位先包含日期時間、地點、備註、是否需要提醒。
- 涉及回診、拿藥、檢查等醫療相關行程時，要標記 `is_medical_related`，但不能讓系統判斷急迫性。
- LINE Bot 可在行程前提醒家屬或看護，但提醒規則要先寫清楚。

請假先做「記錄與通知」，不要做排班系統：

- 看護端可以提出請假時間、原因與備註。
- 家屬端可以看到請假紀錄，並標記已確認。
- 不處理薪資、代理人排班、合約爭議。

### 暫不納入第一版

- 醫院掛號系統串接。
- Google Calendar / Apple Calendar 雙向同步。
- 複雜排班。
- 薪資與扣款計算。
- 勞雇爭議判定。
- 自動判斷醫療急迫性。

這些都可能有價值，但會把產品推進更重的營運和法律責任。先不要混進第一版。

### 資料模型草案

可以先用兩張表，不要塞進既有 `records` 或 `elder_pairings`。

`care_events`

- `id`
- `elder_id`
- `owner_line_user_id`
- `created_by_line_user_id`
- `type`：medical_appointment / rehab / medication_pickup / exam / care_visit / other
- `is_medical_related`
- `title`
- `starts_at`
- `ends_at`
- `location`
- `note`
- `remind_at`
- `status`：scheduled / done / cancelled
- `created_at`
- `updated_at`

`caregiver_leave_requests`

- `id`
- `elder_id`
- `caregiver_line_user_id`
- `owner_line_user_id`
- `starts_at`
- `ends_at`
- `reason`
- `note`
- `status`：pending / acknowledged / cancelled
- `created_at`
- `updated_at`

正式欄位要等資料庫策略定下來再寫 migration。現在先不要直接改 `supabase-schema.sql`。

### 醫療相關提醒文案

`is_medical_related = true` 的行程，只代表這筆行程與回診、檢查、拿藥或復健有關，不代表系統正在做醫療判斷。UI 與 LINE 推播要加上短句：

> 此為一般日程提醒，非醫療指示。

提醒文案不得包含劑量建議、病情判斷、急迫性分級或「應立即就醫」這類判斷。若家屬或看護需要醫療判斷，產品只能提示他們聯絡醫療人員或既有照護窗口。

### 權限邊界

- 家屬是主要建立行程的人。
- 看護可以查看與自己配對長者相關的行程。
- 看護請假由看護建立，家屬只能確認或備註，不要讓家屬代替看護新增請假紀錄。
- 若之後加入機構或多家屬角色，要先重整角色模型，不能硬塞。

### 產品風險

這個功能看起來簡單，但容易踩到幾個問題：

- 回診時間、地點和醫療備註都可能是敏感資料。
- 請假牽涉勞動關係，不能把系統設計成替雇主施壓的工具。
- 提醒漏發可能造成照護風險，所以提醒功能要清楚標示是輔助，不是保證送達。
- 多語文案要小心，不要讓看護誤以為系統在替家屬下命令。

### 下一步

1. 先確認需求提出者要的是「單純提醒」還是「家屬與看護共同管理行程」。
2. 決定正式資料庫路線：VM 自管 Postgres，或 VM app 搭配 managed Supabase。
3. 補 UI 草圖：看護端看行程、家屬端新增行程、看護端請假。
4. 再寫 migration 和 API。
5. 做最小測試：權限、日期範圍、提醒時間、請假狀態。

### v1.1.0 規格整理狀態

OpenSpec change 已建立在 `openspec/changes/v1-1-0-care-calendar/`。目前建議的第一版範圍如下：

- 家屬與看護共同管理已配對長者的照護行程。
- 看護查看自己配對長者的未來 7 天 / 30 天行程。
- 看護提出請假紀錄。
- 家屬查看請假紀錄並標記已確認。
- 請假原因同時支援固定選項與自由文字備註。
- 醫療相關行程只作一般日程提醒，文案固定避開診斷、分流、治療、劑量或急迫性判斷。
- LINE reminder runtime 先不納入 v1.1.0；本輪只保留資料欄位與 UI 說明，等排程、重試與失敗處理確認後再做。
- 正式資料庫 migration 等 VM 自管 Postgres / managed Supabase 決策後再落地。
- 行程與請假資料保留期限先跟照護紀錄一致。
